## 2. Global REST API Standards & Protocols

`[ENGINEERING DECISION]`
All client applications, mobile interfaces, and external integration adapters adhere to standardized REST conventions:

### 2.1 Standard HTTP Status Codes
- `200 OK`: Request succeeded; entity returned in response body.
- `201 Created`: Resource successfully created; returns newly generated entity with `Location` header.
- `204 No Content`: Action succeeded with no body returned.
- `400 Bad Request`: Syntactically malformed request payload.
- `401 Unauthorized`: Missing, expired, or invalid JWT Bearer token.
- `403 Forbidden`: Authenticated user lacks required permission or property scope.
- `404 Not Found`: Resource does not exist within the active property scope.
- `409 Conflict`: Business state collision (e.g., duplicate booking reference, concurrent last-room collision).
- `422 Unprocessable Entity`: Semantic validation failure (Pydantic schema violation).
- `429 Too Many Requests`: Rate limit threshold exceeded.
- `500 Internal Server Error`: Generic unhandled server exception. Stack traces are **never** exposed to clients.

### 2.2 Standard Error Response Schema
Every error generated by the FastAPI backend adheres strictly to the unified envelope:

```json
{
  "error": {
    "code": "ROOM_NOT_AVAILABLE",
    "message": "Requested room is no longer available for the selected dates.",
    "details": {
      "room_type_id": "8fa85f64-5717-4562-b3fc-2c963f66afa6",
      "date": "2026-10-15",
      "available_count": 0
    },
    "request_id": "req-9b1deb4d-3b7d-4bad-9bdd-2b0d7b3dcb6d",
    "timestamp": "2026-10-10T14:32:10.842Z"
  }
}
```

### 2.3 Pagination, Filtering & Sorting Standards
- **Offset & Limit:** Standard query parameters: `?page=1&limit=25` (Max limit = 100).
- **Metadata Envelope:**
  ```json
  {
    "items": [ ... ],
    "pagination": {
      "total_items": 142,
      "page": 1,
      "limit": 25,
      "total_pages": 6,
      "has_next": true,
      "has_prev": false
    }
  }
  ```
- **Sorting:** Standard format: `?sort=-created_at,room_number` (`-` designates descending order).

## 4. Webhook Ingestion & Database-Authoritative Idempotency

`[SOURCE REQUIREMENT]` & `[ENGINEERING DECISION]`
All incoming webhooks (Payment Gateway notifications, OTA booking alerts) adhere to strict security and database-authoritative deduplication invariants. In-memory Redis keys are utilized solely for optional caching acceleration; the PostgreSQL `UNIQUE(provider, event_id)` constraint serves as the authoritative barrier:

```mermaid
sequenceDiagram
    autonumber
    actor External as External Provider (Razorpay / OTA)
    participant Nginx as Nginx Gateway
    participant API as FastAPI Webhook Endpoint
    participant DB as PostgreSQL 16+ (Authoritative)
    participant Queue as Celery Task Queue

    External->>Nginx: POST /api/v1/webhooks/{provider} (Signature Headers + Body)
    Nginx->>API: Pass Request (Raw Bytes)
    
    API->>API: Verify Cryptographic Signature (HMAC-SHA256)
    alt Signature Fails
        API-->>External: 401 Unauthorized ("Invalid Webhook Signature")
    end

    Note over API,DB: Authoritative Deduplication via Database Constraint
    API->>DB: BEGIN TRANSACTION
    API->>DB: INSERT INTO webhook_events (provider, event_id, payload, status) VALUES (:provider, :event_id, :payload, 'RECEIVED') ON CONFLICT (provider, event_id) DO NOTHING
    
    alt Insert Succeeded (First Encounter)
        API->>DB: COMMIT TRANSACTION
        API->>Queue: Enqueue Asynchronous Processing Task (event_pk)
        API-->>External: 200 OK ("Accepted")
    else Conflict / Row Already Exists (Duplicate / Replay)
        API->>DB: ROLLBACK / COMMIT EMPTY
        API-->>External: 200 OK ("Duplicate event received; already acknowledged")
    end
```

## 5. Asynchronous Background Task Specification (Celery Engine)

`[SOURCE REQUIREMENT]` & `[ENGINEERING DECISION]`
Long-running I/O, report rendering, external notifications, and channel synchronization execute asynchronously via Celery worker pools:

| Task Name | Trigger Event | Input Payload | Retry Policy | Dead-Letter Policy | Description |
| :--- | :--- | :--- | :--- | :--- | :--- |
| `task_send_notification` | Business Event (e.g., Booking Created) | `template_code`, `recipient_phone`, `variables_json` | 3 Retries (Backoff: 10s, 30s, 60s) | Move to `failed_notifications` after 3 failures; alert ops. | Dispatches WhatsApp, SMS, or Email via external gateway API. |
| `task_generate_invoice_pdf` | Folio Checkout Finalized | `invoice_id`, `property_id` | 3 Retries (Backoff: 5s, 15s, 30s) | Log Sentry error; front desk can trigger manual re-render. | Renders HTML template via WeasyPrint into PDF; uploads to private S3 bucket. |
| `task_sync_channel_ari` | Inventory / Rate / Restriction Change | `property_id`, `channel_id`, `date_range` | 5 Retries (Exponential backoff: 30s to 15m) | Move to `channel_dead_letter_events`; trigger GM critical alert badge. | Pushes updated room counts and rates to external OTA endpoints. |
| `task_night_audit_rollover` | Celery Beat Daily Schedule (02:00 AM) | `property_id`, `business_date` | 0 Retries (Manual intervention mandatory on crash) | Halt rollover; emit high-priority audit failure notification. | Batch posts room tariffs, verifies shift balances, advances business date. |
| `task_reconcile_gateways` | Hourly Cron | `property_id`, `window_hours` | 2 Retries | Log discrepancy report. | Queries online payment gateway API to reconcile captured vs. pending transactions. |
| `task_cleanup_expired_holds`| Every 5 Minutes Cron | `property_id` | None (Runs continuously) | None. | Releases temporary website cart holds exceeding 15 minutes. |
